# Phase-1 feature-selection reconciliation

The production DuckDB backend implements the `reconcile_feature_selection` capability used by
data-warehouse `2d4550d` and predictor orchestration `a83f7495`.

## Boundary

Authentication belongs to the data-warehouse host. The host rejects an unauthenticated request
before invoking the backend, checks that the backend declares `reconcile_feature_selection`, and
then passes the JSON document to the provider. The provider validates the request again but does
not accept credentials or make authorization decisions.

## Retained evidence

For every `COMPLETED` identity, reconciliation reads the immutable receipt selected by
`envelope_sha256`, authenticates the referenced run from its canonical fields, checks the
receipt's feature membership, and requires retained rows for that feature in at least one of the
six normalized fact families. `UNAVAILABLE` identities are retained in the expected population
without claiming an envelope or receipt.

A successful response is generated by the byte-identical data-warehouse `2d4550d` contract. It
echoes every request-bound field, returns the expected identities in their original order, marks
the population complete, reports no contradictions, and seals the response with
`reconciliation_sha256`. Missing envelopes, altered run identities, invalid receipt membership,
and missing fact rows reject the request instead of producing a partial response.

## Deployment

Install `predictor-olap-store>=0.1.4` and `predictor-duckdb-store>=0.1.2` in the warehouse host
environment, then restart the host through the deployment procedure. The backend must advertise
both `write_feature_selection_envelope` and `reconcile_feature_selection`. No route or credential
logic is implemented in these packages.

The acceptance tests use temporary DuckDB files only. They do not open the populated warehouse
or restart a service.
