Every slot: `systemd --user` timer `fs4-worker@<slot>.timer` (`OnUnitInactiveSec=2min`),
service runs `fs4-worker-once <slot>` → `tools/fs4_worker.py --max-tasks 1`, which
(1) checks the host (MemAvailable ≥ cap + 3 GiB reserve, output root durable, for GPU
slots the UUID listed and ≤ 75 C) and claims nothing when unfit, (2) claims one task
of its arm, (3) runs `FS4_RUNNER` under `crispdm-run -q -m <cap> -t <wall>` with the
task JSON on stdin and `FS4_EXPECTED_GPU_UUID` in the child's environment (the child
re-verifies; there is no CPU fallback), (4) persists the terminal atomically under
`FS4_OUTPUT_ROOT`, (5) delivers it to the coordinator over SSH, and records
**FAILED** with the controller's reason if the delivery is rejected (the local
terminal is set aside as `<task>.json.rejected.<ts>`). A runner refusal (`status`
≠ COMPLETE) is FAILED with the typed reason, never a fabricated number.

Install: `bash tools/fs4_deploy/install_host.sh <slot>` (or `--check-only`), which
refuses while the runner does not answer `--self-check` with a real `code_commit`,
while the cap is a placeholder, while the UUID is not of physical form / not listed /
not seen by TensorFlow, or while the coordinator does not answer `status` for the
configured DB.
